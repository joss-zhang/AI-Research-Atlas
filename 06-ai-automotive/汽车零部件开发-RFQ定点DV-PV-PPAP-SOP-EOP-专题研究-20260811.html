AI-RESEARCH-ATLAS / 汽车产业链质量开发

从一次询价，走到最后一件量产件。

RFQ、定点、DV、PV、PPAP、SOP、EOP 不是七个孤立缩写，而是一条把商业承诺、工程证据、制造能力、客户批准和生命周期责任串起来的质量证据链。

研究日期：2026-08-11案例：高通 SA515M → 移远 AG55xQ → Tier1 T-BOX → 整车框架：AIAG APQP 第 3 版 / PPAP 第 4 版

读完后，你应该能回答：每个阶段到底要把什么风险关掉？谁负责提交什么证据？什么条件满足后才能把责任交给下一阶段？

核心判断：汽车开发的“完成”不是样件能工作，而是需求、设计、过程、产能、批准和持续供货都能被证据追溯。

先校准

三个判断，避免把流程读错。

行业缩写在不同 OEM、Tier1 和芯片供应商内部可能有不同叫法。先固定本页采用的工作口径。

01 / APQP 是主骨架

RFQ 与定点是商务和供应商选择的前置层；定点后，APQP 把产品、过程和反馈活动组织成有门禁的开发计划。APQP 不是一套“交资料”的清单，而是把风险前移。

02 / DV、PV 不是全球唯一释义

本页将 DV 定义为设计验证，将 PV 定义为产品与生产验证。部分企业把 PV 叫产品验证，另一些企业把它叫生产验证；以客户的 DVP&R、试验规范和质量门为准。

03 / PPAP 批准不等于 SOP

PPAP 证明生产意图的零件和过程具备稳定满足要求的能力；SOP 还要看工厂是否能按节拍交付、物流是否就绪、现场是否完成安全投产和爬坡管理。

阅读方式：把每个阶段看成一个“风险关闭器”。阶段输入来自前一阶段的承诺和证据；阶段输出必须是下一阶段能够复用的基线，而不是只在评审会上展示的幻灯片。

七个节点

商业承诺 → 工程证据 → 生命周期退出。

这条路径是项目管理的全局视图。实际项目会有回环：DV 失败会回到设计，PV 失败会回到过程，EOP 也可能因替代料或软件支持重新打开变更。

词典

七个缩写的“工作定义”。

定义用于建立跨供应链的共同语言；具体模板、提交等级、样件数量和时间节点仍受客户特殊要求、合同和项目类型约束。

节点英文 / 中文本页工作定义最容易误解的地方
RFQRequest for Quotation
询价 / 报价		客户邀请供应商基于规格、数量、节拍和商务条款提交可执行报价。不是只报一个单价；报价必须包含假设、产能、模具、开发费用、认证、风险和交付边界。
定点Nomination / Award
项目定点		客户在候选供应商中授予项目或零件业务，锁定初始商业和开发责任。定点不是“所有设计已冻结”，工程输入、接口、变更和目标仍需通过后续评审逐步收敛。
DVDesign Verification
设计验证		用测试、分析和审查证明设计输出满足设计输入、法规和接口要求。实验室样件通过不代表量产过程稳定，也不代表整车环境和生产意图状态已经验证。
PVProduct / Production Validation
产品 / 生产验证		用生产意图的产品、设备和过程，在代表性环境中验证产品能用、过程能造。“PV”在不同公司含义不同；必须在项目计划里写明测试对象、样件状态和判定标准。
PPAPProduction Part Approval Process
生产件批准程序		供应商证明实际生产过程能在规定生产速率下持续制造符合设计记录和规格的零件，并提交客户批准。PPAP 不是把 DFMEA、尺寸报告打包上传就结束；客户批准状态、偏差关闭和生产批次真实性同样关键。
SOPStart of Production
量产启动		项目进入正式系列生产与交付，生产、物流、质量、服务和软件版本开始按运营机制管理。SOP 是起点不是终点；安全投产、爬坡、早期遏制和现场问题闭环往往决定项目是否真正成功。
EOPEnd of Production
生产结束		车型、平台或零件的系列生产结束，进入收尾、备件、库存、工具和技术支持管理。不能只关掉生产工单；电子零件还要处理芯片生命周期、固件、密钥、数据、售后和替代料。

APQP 主骨架

把七个项目节点放回五个质量阶段。

AIAG 在 2024 年发布 APQP 第 3 版，并把 Control Plan 独立成单独手册；新版增加了采购、变更管理、项目指标、风险缓解、门禁管理和零件追溯等内容。

阶段 1
项目策划与定义

把客户之声、法规、项目目标、供应链策略、风险与时间表转成初始质量计划。RFQ 可以提前使用其中的估算活动，但正式 APQP 计划通常在项目被定义后展开；定点是供应商责任落地的关键输入。

阶段 2
产品设计与开发

建立设计记录、系统与零件需求、设计评审、DFMEA、DVP&R、样件计划、接口和变更控制。DV 是这一阶段的主要证据门。

阶段 3
过程设计与开发

把已确认的产品设计转成可制造的流程：流程图、PFMEA、控制计划、工装、检具、作业指导、包装、人员培训和过程能力计划。PV 的过程侧在这里打底。

阶段 4
产品与过程验证

用生产意图零件和实际生产条件完成试生产、MSA、初始过程能力、性能与可靠性、包装和节拍验证，形成 PPAP 提交证据。PPAP 是客户批准门，不是所有验证活动的替代物。

阶段 5
反馈、评价与纠正措施

SOP 后用量产数据、保修、客户投诉、现场故障、供应商表现和成本质量指标反馈到设计与过程；EOP 则把停产、备件、变更、追溯和知识归档纳入项目闭环。

工具链的依赖关系：客户需求 → 设计记录 → DFMEA / DVP&R → 过程流程 → PFMEA → 控制计划 → MSA / SPC → 试生产数据 → PPAP / PSW → SOP 运行数据。前一项没有形成基线，后一项就只能“补材料”，不能真正证明风险已关闭。

贯穿案例

一颗芯片如何变成一辆车里的 T-BOX。

案例选用高通 SA515M 与移远 AG55xQ，是因为移远官方资料明确说明 AG55xQ 基于符合 AEC‑Q100 的 SA515M 芯片，并面向 T‑Box、TCU、ADAS、C‑V2X 等汽车应用。

Tier 2 / 芯片高通 SA515M

汽车级 5G 蜂窝通信芯片。关注芯片规格、AEC‑Q100、软件基线、供货周期、生命周期和芯片级变更。

→
Tier 2 / 模组移远 AG55xQ

车规 5G Sub‑6 模组，支持 SA/NSA、4G/3G/2G 回落、GNSS、可选 C‑V2X/DSDA，负责把芯片能力变成可集成的标准接口。

→
Tier 1 / 系统T-BOX 集成

Tier1 负责主板、电源、天线、GNSS、MCU/应用处理器、CAN/以太网、诊断、OTA、安全、结构与生产工艺。

→
OEM / 整车整车集成

整车厂验证网络覆盖、车端数据、eCall、远程控制、车云闭环、整车 EMC、法规、用户体验和量产交付。

平台边界：高通 X75 是另一款面向 5G Advanced 的 Modem‑RF System，官方参数不能直接等同于 SA515M 或 AG55xQ。若项目改用 X75，应重新核对芯片—模组配对、射频前端、软件、认证、热设计、BOM 和 PPAP 证据。

七段拆解

每一阶段，交付什么才算真的向前走？

以下内容按“目标—做什么—关键点—交付物—放行条件—常见失败”展开。项目应把它转化为带责任人、日期、状态和证据链接的 APQP 主计划。

01
RFQ

询价报价：把一句需求变成一份可执行承诺。

RFQ 是商业入口，也是第一次识别技术、供应链、认证和生命周期风险的机会。

报价基线

做什么

解析 OEM 的 RFQ、技术规范、SOR、预测量、SOP/EOP、地区和法规要求，建立需求假设与问题清单；由销售、采购、硬件、软件、射频、质量、制造、物流和财务共同核算报价。

案例落地：T-BOX 5G

确认网络制式与频段、SA/NSA、4G 回落、GNSS 精度、eCall、C‑V2X、DSDA、天线数量、CAN/以太网接口、供电、温度、EMC、OTA、年需求和地区认证，再判断 SA515M + AG55xQ 是否满足边界。

关键交付物

报价单与成本分解RFQ 假设与偏差表BOM / 供应商初选开发与认证报价产能与投资计划初始风险清单项目主时间表质保与服务假设

放行条件与失败模式

  • 所有客户要求都有“满足 / 偏差 / 待澄清”状态，并由客户确认关键假设。
  • 长周期芯片、模组固件、射频认证、天线和测试设备已纳入交期与现金流。
  • 避免低价中标后再发现认证、夹具、云服务、备件和 EOP 责任没有报价。
02
定点

项目定点：锁定“谁来做、做什么、按什么规则做”。

定点把候选方案变成客户授予的项目责任，但不是把所有工程不确定性伪装成已冻结。

业务授予

做什么

完成供应商技术、质量、商务、产能和合规评审，确定芯片、模组、Tier1 和 OEM 的边界；签署定点通知、采购合同、SOW、目标价格、预测量和项目门禁。

案例落地：四方责任

高通负责 SA515M 的芯片与支持边界；移远负责 AG55xQ 模组、模组软件和认证支持；Tier1 负责 T‑BOX 系统设计与制造；OEM 负责整车需求、客户特殊要求、整车验证和最终批准。

关键交付物

定点通知 / 采购合同SOW 与接口矩阵版本化需求基线责任矩阵 RACIAPQP 主计划DVP&R 初版长周期物料计划变更与偏差流程

放行条件与失败模式

  • 定点文件写清零件号、软件版本、区域变体、产能、工厂、SOP、EOP 和售后责任。
  • 对“供应商自选”与“客户指定”料件标记责任差异，避免 Tier1 承担无法控制的质量风险。
  • 避免只签价格不签版本；芯片、模组和云端接口的版本漂移会把 DV/PV 重新变成救火。
03
DV

设计验证：证明设计“理论上与实验室里”满足输入。

DV 关掉的是设计缺陷风险，重点是需求覆盖、边界条件和可重复的测试证据。

设计可行

做什么

将 OEM 需求分解到 T‑BOX、主板、模组、芯片、软件和天线，形成需求—设计—测试的可追溯矩阵；执行 DVP&R 中的电气、射频、通信、热、机械、EMC、定位、可靠性与安全测试。

案例落地：从芯片到模组

  • 芯片级：确认 SA515M 供电、时钟、接口、电源状态、热阻、软件包、射频配置和生命周期。
  • 模组级：验证 AG55xQ 的 SA/NSA、4G 回落、MIMO、GNSS、SIM、USB/PCIe/UART、AT 指令、DFOTA、C‑V2X 选项。
  • 系统级：验证 T‑BOX 天线布局、CAN/以太网、唤醒、低功耗、数据上报、远程控制和车云接口。

关键交付物

需求追溯矩阵系统 / 硬件 / 软件设计记录DFMEADVP&R 与测试报告接口控制文件射频与 EMC 预扫描样件问题清单工程变更记录

放行条件与失败模式

  • 每项需求都有测试方法、样件状态、版本、环境、判定标准、原始数据和结论。
  • 关键失效模式必须有纠正措施和回归测试，不能用“下版优化”替代关闭。
  • 避免拿开发板或非量产天线的通过结果宣称设计冻结；量产器件、热设计和结构约束必须在 DV 后收敛。
04
PV

产品 / 生产验证：证明“这套产品能造出来，也能在车上工作”。

PV 把实验室的设计证据带到生产意图、整车环境和代表性生产节拍中。

量产意图

做什么

使用量产意图的芯片、模组、PCB、结构、软件和工装，在目标工厂以计划节拍进行试生产；将 T‑BOX 装车，执行整车环境、道路、网络、云端、法规和服务场景验证，同时验证过程流程、检具、人员、包装和物流。

案例落地：生产意图试验

  • 车辆环境：冷启动、热浸、振动、湿热、盐雾、ESD、EMC、天线遮挡、弱覆盖和跨网切换。
  • 功能闭环：紧急呼叫、远程诊断、OTA 断点续传、车辆状态上报、CAN 信号一致性、GNSS 漂移与组合导航。
  • 制造验证：首件、工位防错、烧录与密钥注入、射频校准、终检、追溯、包装、Run at Rate。

关键交付物

生产意图样件过程流程图PFMEA控制计划作业指导书MSA 计划与结果初始过程能力试生产 / 节拍报告包装与物流验证问题关闭记录

放行条件与失败模式

  • 试生产的设备、人员、物料、工艺参数和检验方法与未来量产一致，偏差必须登记。
  • 过程能力不足时先改善或制定客户批准的临时控制，不能把试生产数据美化成量产能力。
  • 避免只测“功能能否运行”，却没有覆盖烧录失败、版本错配、天线装反、密钥丢失和网络长期在线等制造失效。
05
PPAP

生产批准：把“我们认为可以”变成客户可审计的批准。

PPAP 的核心是证明实际生产运行具备持续满足设计记录和规格的能力。提交等级、样件数量和额外要求由客户决定。

客户批准

做什么

基于 PV 的真实生产批次整理 PPAP 包，逐项确认设计记录、变更、工程批准、DFMEA、流程图、PFMEA、控制计划、MSA、尺寸、材料 / 性能、初始能力、实验室资质、样件、主样、检具、CSR 和 PSW。

案例落地：电子 T‑BOX 的证据重点

  • 硬件：PCB 版本、BOM、芯片 / 模组批次、关键尺寸、焊接与涂覆、材料声明和可靠性。
  • 软件：烧录镜像、版本校验、配置与标定、网络参数、Secure Boot / OTA 变更记录（按客户的软件批准流程）。
  • 系统：整车接口、EMC、eCall、GNSS、C‑V2X、诊断、数据安全和包装标签的客户批准。

典型提交物

PSW设计记录与变更文件DFMEA / PFMEA流程图 / 控制计划MSA尺寸与材料报告性能 / 可靠性报告初始过程研究实验室资质样件 / 主样 / 检具客户特殊要求

放行条件与失败模式

  • 提交包的零件号、版本、样件批次、生产地点和数据相互一致，PSW 结论与实际证据一致。
  • 客户批准状态应明确为批准、临时批准或拒绝；临时批准必须有到期日、遏制和关闭计划。
  • 客户特殊要求可能要求 PSO、Run at Rate、额外软件或网络安全证据；不能用“AIAG 标准没要求”拒绝客户要求。
06
SOP

量产启动：把开发项目交给日常运营，但保留一段安全缓冲。

SOP 是从“项目交付”切换到“持续供货”的运行门；最关键的是安全投产、稳定爬坡和异常升级。

可稳定交付

做什么

按已批准的零件、软件、工艺和控制计划生产；实施 Safe Launch / Early Production Containment，监控缺陷、直通率、停线、节拍、交付、版本和现场问题；以日 / 周节奏完成爬坡。

案例落地：T‑BOX 量产运行

  • 入料验证：SA515M 与 AG55xQ 的批次、标签、固件、校准与供应商变更状态。
  • 工艺防错：SMT、射频测试、烧录、密钥注入、CAN/以太网测试、整机老化、序列号和云端激活。
  • 运营指标：一次合格率、现场失效率、通信注册成功率、OTA 成功率、误报率、返修率和供应商交付。

关键交付物

安全投产计划量产控制计划工位 / 检测记录批次与序列号追溯版本与配置基线产能 / 节拍日报异常升级清单运营交接包

放行条件与失败模式

  • 按客户定义的指标连续稳定运行，安全投产退出条件有数据而非口头承诺。
  • 任何芯片 PCN、模组固件、网络参数或云端 API 变化都必须进入变更评估和再批准流程。
  • 避免把 SOP 当作“首批货发出”；量产控制、备件策略、软件发布和现场服务若未就绪，项目仍未真正落地。
07
EOP

项目结束：结束生产，不结束责任。

EOP 是生命周期治理的最后一道门，目标是零件、备件、工具、软件和数据有序退出，避免停产造成断供与合规风险。

有序退出

做什么

接收 OEM 停产通知和最后需求预测，制定最后生产、库存消化、替代料、售后备件、工具保管、资料归档、供应商退出、软件支持和网络安全处置计划。

案例落地：5G T‑BOX 的 EOP

  • 芯片：确认 SA515M 生命周期、最后采购、替代芯片评估和是否需要重新 DV/PV/PPAP。
  • 模组：冻结 AG55xQ 最后版本，保留固件、校准、认证、密钥与维修刷写能力。
  • 整车：管理最后一批车、备件需求、云服务接口、证书 / 密钥生命周期、数据保留与删除。

关键交付物

EOP 通知与最后需求最后采购 / 库存报告备件与售后计划工具 / 检具处置记录软件与安全归档替代料与变更评估质量数据与经验教训项目关闭报告

放行条件与失败模式

  • 最后一批产品、在制品、原材料、备件和供应商开放订单有可核对的账。
  • 不得未经客户书面确认擅自报废客户工具、关键材料或技术资料；售后供货义务要有合同依据。
  • 避免只看库存金额，不看网络连接、OTA、证书、云端和维修工具的长期可用性。

交接设计

上一阶段的输出，必须成为下一阶段的输入。

如果交接物没有版本、责任人和证据位置，项目会在每个门重新争论“到底按哪一版做”。

前一阶段必须交给下一阶段的基线下一阶段首先检查什么
RFQ → 定点报价假设、成本 / 产能边界、供应商方案、风险和偏差。定点是否覆盖全部承诺？哪些要求仍待澄清？谁承担不可控的芯片和网络风险？
定点 → DVSOW、零件 / 软件版本、需求矩阵、接口、DVP&R、责任和里程碑。需求是否可测试？SA515M—AG55xQ—T‑BOX 的接口边界是否有单一责任人？
DV → PV设计记录、已关闭关键 DFMEA 风险、DVP&R 结果、量产意图差异清单。试生产样件是否与验证通过的设计一致？量产天线、工装、固件和参数是否已纳入？
PV → PPAP真实生产批次、流程图、PFMEA、控制计划、MSA、能力、性能和问题关闭证据。数据是否来自规定的生产速率？提交包中的批次、版本、工厂和零件号是否一致？
PPAP → SOP客户批准的 PSW、偏差 / 临时批准状态、批准版本和安全投产条件。批准是否覆盖当前软件和硬件？现场是否具备已批准的工艺、检测、包装和物流能力？
SOP → EOP量产质量、交付、保修、变更、库存、备件、生命周期和云端运行数据。停产是否会造成断供、售后缺件、芯片过时、证书失效或软件服务中断？

责任矩阵

四层供应链，四种“完成”。

供应商层级越高，交付物越接近整车和客户体验；但下游不能把上游的认证或芯片等级直接当作系统合格。

主体主要负责必须提供给下游的证据不能替下游证明的事情
高通 / 芯片供应商芯片规格、参考设计、软件支持、PCN、生命周期、芯片级质量和供货承诺。数据手册、应用说明、芯片质量 / 变更资料、生命周期与支持窗口。不能替 T‑BOX 证明天线布局、整车 EMC、生产节拍和整车网络体验。
移远 / 模组供应商模组硬件、射频、固件、驱动、认证支持、校准、技术支持和模组级变更。AG55xQ 规格、硬件设计资料、AT / 驱动、认证、DFOTA、质量与 PCN 资料。不能替 Tier1 证明 T‑BOX 主板、电源、装配、烧录、密钥和整车接口。
Tier1 / T‑BOX 集成商系统架构、软硬件集成、天线、车载接口、生产过程、测试、PPAP 和交付。系统需求矩阵、DFMEA/PFMEA、DVP&R、控制计划、PV 数据、PPAP、量产追溯。不能用模组的“车规级”宣传替代整机与整车验证，也不能单方面改动客户需求。
OEM / 整车厂整车需求、客户特殊要求、车型计划、整车集成、最终批准、售后和 EOP 决策。SOR、接口和法规要求、客户批准状态、车型预测、EOP 通知及服务策略。不能只以整车试验结果替代供应商过程能力和 PPAP 证据。

立即落地

项目经理今天就可以开这张表。

把“有没有资料”改成“证据是否能支持放行”。每一行都应有责任人、计划完成日、当前状态和证据链接。

  • 把 RFQ 的客户要求拆成需求编号、版本、验证方法、责任主体和报价影响。
  • 在定点文件中锁定芯片、模组、T‑BOX、工厂、区域变体、SOP/EOP 与售后边界。
  • 建立 SA515M → AG55xQ → T‑BOX → 整车的接口控制文件，所有版本可追溯。
  • 让 DVP&R 覆盖电气、射频、热、机械、EMC、GNSS、网络、诊断和安全，而不只覆盖功能演示。
  • 在 PV 前冻结生产意图物料、软件、天线、工装、测试设备、人员和工艺参数。
  • 把 DFMEA 的高风险项落实到 PFMEA、控制计划和工位防错，形成证据链。
  • 以真实生产批次做 MSA、初始能力、节拍、追溯、包装和 PPAP 数据，拒绝“实验室数据冒充量产数据”。
  • 在 PSW 上明确批准、临时批准或拒绝，临时批准必须有遏制、到期日和关闭责任。
  • SOP 后设置安全投产与爬坡指标，监控一次合格率、现场失效、OTA、网络注册、停线和交付。
  • 把芯片 PCN、模组固件、云端 API、证书、密钥、替代料和网络退网纳入变更评估。
  • EOP 前完成最后采购、库存消化、备件、工具、软件、数据与安全归档，并得到客户书面关闭。
  • 每个阶段评审只允许三种结论：放行、带条件放行（有期限和遏制）、不放行；不接受没有证据的口头绿灯。

核心结论

真正成熟的汽车零部件项目，不是把 RFQ 变成一张订单，而是把每次承诺都转化为下一阶段可复用、可审计、可追溯的证据；谁能把芯片生命周期、模组版本、T‑BOX 制造和整车服务连成一条不断链的证据链，谁才真正具备从定点走到 EOP 的交付能力。
