CHAPTER 01

先把三个容易混淆的概念拆开

图数据库是存储技术，知识图谱是组织知识的产品形态，本体是约束语义的显式模型。三者可以组合，但不是同义词。

一句话记忆：本体是“可计算的共同语言”，知识图谱是“用这种语言陈述的事实网络”。

ONTOLOGY · 本体

定义“世界的规则”

对某一领域中的概念、关系与约束进行显式、形式化、共享的说明。它回答：什么是车辆？车型和车辆实例有何不同？电池包一定是零部件吗？“装配于”与“包含”是否互逆？

KNOWLEDGE GRAPH · 知识图谱

记录“世界的事实”

以图结构组织实体、关系、属性与上下文，并可附带模式、来源和质量信息。它回答：VIN-001 装了哪块电池？该电池由谁供应？受哪个召回活动影响？

蓝图与建筑本体规定梁柱、门窗和连接规则；图谱是按蓝图落成并持续入住的建筑。
语法与文章本体给出词类和句法；图谱是用这些规则写出的、可被机器理解的事实文本。
宪法与社会本体定义角色、权利与约束；图谱记录个体以及正在发生的关系与事件。

目标质量追溯 + 主动服务

Q6

CHAPTER 03

从零构建汽车本体

本体工程不是一次性“把所有名词收齐”，而是围绕能力问题反复迭代：定义范围、复用词汇、建类与关系、加入约束、实例验证。

确定领域与用例

服务于“车辆质量追溯与主动服务”，不试图成为整个汽车世界的百科全书。

列出能力问题

让每个类、关系和约束都能回到一个待回答的问题，避免无业务消费方的建模。

盘点与复用

复用 RDF/RDFS/OWL、PROV-O、Schema.org、ASAM 与 Catena-X 中适合的概念，记录映射而非机械照搬。

建立概念模型

先用领域语言画类层级、对象关系和事件，再决定哪些是类、实例、属性或受控词表。

形式化公理

加入 domain/range、基数、互逆、不相交、传递与属性链；选择能满足推理需求的最小表达力。

定义质量形状

OWL 表达“世界可能如何”，SHACL 验证“本批数据是否符合接入合同”；两者职责不同。

用实例回放

装入 20—50 个真实结构的样例，执行能力问题、反例和边界测试，再评审命名与粒度。

类体系：区分“类型、实例、事件与状态”

四个决定模型质量的建模模式

PATTERN 01

车型 ≠ 单车

“星驰 E7”是产品型号；“VIN-001”是带生产日期、里程和当前装配状态的车辆实例。混为一谈会让召回范围与配置规则失真。

PATTERN 02

零件类型 ≠ 序列化零件

“77kWh 电池包”是规格；“BP-77A-2309”是某一实物。质量追溯必须落到序列号与生产批次。

PATTERN 03

状态用带时间的观测表达

电池健康度会变化，不应永远写成电池的单一属性。建成“健康度观测”节点，连接数值、时间和来源。

PATTERN 04

有属性的关系升级为事件

“安装”若需要安装时间、工位、操作员和来源，就建成装配事件，而不是只有一条无法挂载上下文的边。

对象属性、数据属性与约束

语义项类型定义域 → 值域关键约束例子
属于车型对象属性Vehicle → VehicleModel每辆车恰好 1 个车型VIN-001 → 星驰E7
装配零件对象属性Vehicle → ComponentInstance与“装配于车辆”互逆VIN-001 → BP-77A
运行软件对象属性ECU → SoftwareRelease通过安装事件保留时间BMS-001 → v4.2.1
由…供应对象属性ComponentType → Supplier不可直接套到实物批次77kWh电池 → 蓝湾能源
车辆识别码数据属性Vehicle → xsd:string恰好 1 个、17 位、全局唯一LXC7…0001
健康度数值数据属性HealthObservation → xsd:decimal0—100，必须有观测时间87.4

公理让模型从“词表”升级为“可推理规则”

BEV ⊑ Vehicle

纯电汽车一定是汽车；类型继承。

BEV ⊓ ICEVehicle ⊑ ⊥

纯电汽车与燃油汽车不相交；发现双重类型即矛盾。

hasPart ≡ inverse(partOf)

“包含零件”和“属于总成”互逆，可自动补全反向关系。

partOf ○ partOf ⊑ partOf

零件属于子总成、子总成属于整车，可推得零件间接属于整车。

Vehicle ⊑ (=1 hasVIN)

每个车辆实例恰好一个 VIN；属于概念约束。

hasPart ○ suppliedBy ⊑ exposedTo

车辆装配某件且该件来自某供应商，可推得车辆暴露于该供应商风险。

把本体写成 Turtle / OWL

ontology.ttl · 核心片段
@prefix auto: <https://atlas.example/auto/> .
@prefix owl:  <http://www.w3.org/2002/07/owl#> .
@prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#> .
@prefix xsd:  <http://www.w3.org/2001/XMLSchema#> .

auto:Vehicle a owl:Class .
auto:BatteryElectricVehicle a owl:Class ;
  rdfs:subClassOf auto:Vehicle ;
  owl:disjointWith auto:ICEVehicle .
auto:ComponentInstance a owl:Class .
auto:Supplier a owl:Class .

auto:hasComponent a owl:ObjectProperty ;
  rdfs:domain auto:Vehicle ;
  rdfs:range auto:ComponentInstance ;
  owl:inverseOf auto:installedOn .

auto:hasVIN a owl:DatatypeProperty, owl:FunctionalProperty ;
  rdfs:domain auto:Vehicle ; rdfs:range xsd:string .

auto:Vehicle rdfs:subClassOf [
  a owl:Restriction ; owl:onProperty auto:hasVIN ;
  owl:cardinality "1"^^xsd:nonNegativeInteger
] .

注意开放世界假设：图中“没有写”通常表示未知，不自动表示不存在；不同 IRI 也不自动代表不同个体。需要唯一性或闭集校验时，应结合标识策略与 SHACL。

SHACL：在装载前拦住坏数据

shapes.ttl · 车辆数据合同
@prefix sh: <http://www.w3.org/ns/shacl#> .
@prefix auto: <https://atlas.example/auto/> .
@prefix xsd: <http://www.w3.org/2001/XMLSchema#> .

auto:VehicleShape a sh:NodeShape ;
  sh:targetClass auto:Vehicle ;
  sh:property [
    sh:path auto:hasVIN ; sh:minCount 1 ; sh:maxCount 1 ;
    sh:datatype xsd:string ; sh:pattern "^[A-HJ-NPR-Z0-9]{17}$" ;
    sh:message "车辆必须具有一个合法的17位VIN"@zh
  ] ;
  sh:property [
    sh:path auto:instanceOfModel ; sh:minCount 1 ; sh:maxCount 1 ;
    sh:class auto:VehicleModel
  ] .
结构完整

必填关系、基数、值域与数据类型。

业务合法

VIN 格式、SOH 范围、版本命名规则。

语义一致

对象类型符合 domain/range，不相交类无冲突。

可追溯

关键事实带来源、采集时间与版本。

CHAPTER 06

查询、推理与验证：图谱如何产生答案

查询检索已经存在的路径；推理依据公理或规则产生新事实；验证判断数据是否满足接入合同。三者要分开设计与监控。

SPARQL：查找目标批次且软件需要升级的车辆

query.sparql
PREFIX auto: <https://atlas.example/auto/>
SELECT ?vin ?battery ?version
WHERE {
  ?vehicle a auto:Vehicle ;
    auto:hasVIN ?vin ;
    auto:hasComponent ?battery .
  ?battery auto:fromBatch auto:batch/CELL-2026-04 ;
    auto:containsController ?bms .
  ?bms auto:runsSoftware ?software .
  ?software auto:semanticVersion ?version .
  FILTER(?version < "4.2.3")
}

预期结果

vinbatteryversion
LXC…001BP-77A-23094.2.1

生产环境不要用字符串直接比较语义版本，应在 ETL 中拆为 major/minor/patch 或使用自定义函数。

同一语义也可投影为属性图与 Cypher

query.cypher · 属性图实现
MATCH (v:Vehicle)-[:HAS_COMPONENT]->(b:BatteryPack)
      -[:CONTAINS_CONTROLLER]->(ecu:ECU)-[:RUNS]->(sw:SoftwareRelease),
      (b)-[:FROM_BATCH]->(:Batch {batchNo: 'CELL-2026-04'})
WHERE sw.major = 4 AND (sw.minor < 2 OR sw.patch < 3)
RETURN v.vin, b.serialNo, sw.version

RDF/OWL 更强调开放世界、全球标识、标准语义与推理；属性图更直接地把属性挂在节点和关系上，适合工程遍历。选择应由互操作与推理需求决定，而不是阵营偏好。[10]

规则推理：从供应商风险得到受影响车辆

蓝湾能源发生停产风险
CELL-2026-04由其供应
BP-77A-2309来自该批次
VIN-001装配该电池
风险车辆名单新推得事实 + 证据路径
construct.sparql · 生成风险关系
CONSTRUCT { ?vehicle auto:exposedToRisk ?risk . }
WHERE {
  ?vehicle auto:hasComponent ?part .
  ?part auto:fromBatch ?batch .
  ?batch auto:suppliedBy ?supplier .
  ?supplier auto:hasActiveRisk ?risk .
}

三种“推理”不要混为一谈

方式输入输出特点适合汽车场景风险
描述逻辑推理OWL 公理可证明、一致性可检查类型归类、互逆、传递、不相交冲突表达力越强，计算成本越高
业务规则推理SPARQL规则/规则引擎可解释、贴近流程召回筛选、供应风险传播、保养资格版本与优先级冲突
统计/向量推断图嵌入、GNN、LLM给概率或候选实体匹配、缺失关系推荐、GraphRAG不是事实，必须保留置信度与人工确认
CHAPTER 07

工程落地：把图谱当作长期产品运营

知识图谱上线不是“导入一次数据”。汽车产品和软件持续变更，图谱必须具备版本、来源、时间、质量和责任治理。

01 · 源系统层

保留权威事实源

PLM、MES、ERP、TSP、DMS 不被图谱取代；图谱保存规范身份、连接和来源指针。

02 · 语义接入层

映射与增量管道

CDC、流式事件、批处理、文档抽取；统一单位、代码表、时间与标识。

03 · 语义治理层

本体与形状仓库

本体版本、SHACL、映射、规则、数据契约、评审与兼容策略。

04 · 图存储层

RDF 或属性图

按推理、互操作、遍历与性能选择；可双模投影，但语义源保持唯一。

05 · 计算层

查询与推理

SPARQL/Cypher、规则物化、图算法、向量索引与证据路径。

06 · 服务层

面向任务的接口

质量追溯、召回筛选、售后助手、供应风险与 GraphRAG API。

07 · 观察层

质量与使用反馈

新鲜度、完整性、冲突率、查询延迟、人工修正与业务收益。

08 · 安全层

贯穿全部层

分域权限、行列/子图控制、审计、脱敏、最小化采集和数据主权。

六个常见反模式

把所有名词都建成类

先问是否需要独立身份、关系和生命周期；枚举值可用 SKOS 概念或属性。

用类层级表达零件包含

“电池包是零件”才是 subclass；“电芯属于电池包”应是 partOf。

把未知当作否定

开放世界中无记录不代表不存在；需要闭集检查时用 SHACL 或业务规则。

让 LLM 直接写入权威图谱

模型应生成候选三元组并带证据与置信度，经约束和人工审批后发布。

忽略时间与来源

软件版本、装配状态、里程和供应关系都会变化；没有时间和来源就无法审计。

先选图库再找问题

图数据库不自动产生知识。先写能力问题和消费接口，再决定图模型与平台。

可立即执行的交付清单

  • 列出 5—10 个可验收的能力问题
  • 明确本体边界、领域专家和业务所有者
  • 建立稳定 IRI / 业务主键策略
  • 区分车型、单车、零件类型与零件实例
  • 把带时间/来源的关系建成事件或观测
  • 复用标准词汇并保存映射依据
  • 用 20—50 个实例回放能力问题
  • 为入口类建立 SHACL 数据合同
  • 建立实体合并、拆分和人工修正流程
  • 关键事实保存来源、时间、版本与置信度
  • 推理结果与原始事实分图或分标记保存
  • 定义本体变更的兼容、迁移与回滚策略
  • 跟踪完整率、一致率、新鲜度与冲突率
  • 用业务指标验证图谱是否值得维护
CHAPTER 08

总结：把语义、事实与证据连成闭环

学习到这里，应能独立解释本体与知识图谱的区别，并从一个汽车业务问题出发完成最小可用图谱设计。

你应掌握的建模判断

类、实例、关系、属性、事件

稳定类型建成类；有独立身份的个体建成实例；连接两个实体的语义建成关系；简单值建成数据属性；需要时间、来源或参与方的变化建成事件/观测。

你应掌握的工程判断

语义、质量、来源、生命周期

本体不是数据质量工具的替代品；OWL、SHACL、标识策略、实体消歧、来源记录与版本治理共同构成可信知识图谱。

推荐资料与标准

  1. W3C：RDF 1.1 Concepts and Abstract Syntax——三元组、IRI、字面量与 RDF 图。
  2. W3C：OWL 2 Web Ontology Language Primer——类、属性、公理与推理入门。
  3. W3C：SPARQL 1.1 Overview——RDF 查询、更新、联邦查询与推理制度。
  4. W3C：Shapes Constraint Language——用形状描述并验证 RDF 图。
  5. Stanford：Ontology Development 101——经典本体工程方法。
  6. W3C：Data on the Web Best Practices——持久标识、来源、质量和版本。
  7. Schema.org：Automotive Extension——面向零售车辆、配置、发动机与商业特征的词汇。
  8. ASAM OpenXOntology——道路、交通参与者、环境与自动驾驶场景的本体架构。
  9. Catena-X CX-0002：Digital Twins——汽车数据空间中的唯一标识、数字孪生与语义模型。
  10. Neo4j：Property Graph Concepts——节点、关系、标签与属性图。
  11. Hogan 等：Knowledge Graphs，ACM Computing Surveys 54(4)，系统综述图数据模型、查询、模式与知识图谱构建。
  12. SAE J3164_202301——自动驾驶车辆行为与机动的本体和词汇。
核心结论

本体决定知识图谱能否“说同一种语言”，实例与来源决定它能否“陈述可信事实”，查询、推理和治理决定这些事实能否持续转化为汽车研发、质量、供应与服务决策。
